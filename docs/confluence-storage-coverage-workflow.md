# Confluence Storage coverage workflow

This document records practical findings from reading, expanding, dry-running,
and updating a Confluence Cloud page whose purpose is to exercise a broad set
of page-body representations.

The central conclusion is:

> Markdown is the user-facing working representation. Confluence Storage is
> the source of truth for coverage and round-trip preservation.

## Sources of truth

A complete page check requires more than one artifact.

- `page.api-v2.json` is authoritative for page ID, title, space ID, parent,
  status, version, and other API metadata.
- `body.storage.xml` is authoritative for page-body elements, attributes,
  macros, resource identifiers, and presentation details.
- `page.md` is the primary human and Agent editing surface, but it is a
  projection and cannot prove Storage coverage by itself.
- `page.attributes.json` preserves mappings, presentation attributes,
  identifiers, and opaque extensions needed for safe Markdown round trips.

The detailed public Atlassian Storage reference is published for Confluence
Data Center. It is useful as a category catalog, but it is not by itself proof
that a construct is accepted or generated by Confluence Cloud. Prefer Storage
retrieved from the target Cloud site as the primary fixture, then use the
Data Center reference to identify missing categories.

- [Confluence Storage Format](https://confluence.atlassian.com/doc/confluence-storage-format-790796544.html)
- [Confluence Cloud REST API v2: Page](https://developer.atlassian.com/cloud/confluence/rest/v2/api-group-page/)

## Four coverage levels

Do not collapse coverage into a single supported/unsupported flag.

1. **Recognition coverage**: the runtime can parse and identify a Storage
   element or attribute.
2. **Markdown projection coverage**: the construct has a natural, readable
   Markdown representation.
3. **Preservation coverage**: constructs without a natural Markdown form are
   retained exactly or through an explicit opaque extension.
4. **Editable round-trip coverage**: the user can change the Markdown while
   unchanged Storage details remain valid in the generated candidate.

Recognition and preservation should be established before claiming that a
construct is editable through Markdown.

## Useful Storage coverage categories

A representative standalone page can cover these categories without external
assets or third-party application contracts.

- headings `h1` through `h6`, paragraphs, empty paragraphs, hard breaks,
  horizontal rules, and preformatted text
- bold, italic, underline, strikethrough, inline code, subscript,
  superscript, and nested inline styles
- font size, foreground color, background color, alignment, and indentation
- flat and nested unordered and ordered lists, including a non-default start
- complete and incomplete `ac:task-list` tasks
- regular tables and tables with `rowspan` or `colspan`
- external links and `ac:link` plus `ri:page` internal links
- inline and rich-body `ac:structured-macro` examples
- multi-paragraph block quotes
- Confluence-managed identifiers such as `local-id`, `ac:local-id`, and
  `ac:macro-id`

Keep these as separate fixtures or scenarios when they need real resources or
special editor context:

- attachments and attached images
- external images
- page layouts
- template variables and instructional text
- third-party application macros

No single page can meaningfully cover every Confluence macro. Define the
fixture scope explicitly and use multiple fixtures for external-resource and
application-specific behavior.

## Choosing the update path

Use the Markdown preservation workflow when the user's goal is normal page
editing:

1. export the current page or subtree
2. convert the finalized snapshot to Markdown
3. edit `page.md` without changing opaque extension blocks unintentionally
4. inspect preservation mappings
5. prepare an immutable digest-bound update plan
6. review and explicitly approve the exact plan
7. apply once and inspect its postcondition

Use a direct Storage update only when the purpose is to deliberately add or
restructure Storage constructs that Markdown cannot synthesize. A compact
`confluence-extension` block can preserve a known source fragment, but it must
not be treated as a general-purpose way to author arbitrary new Storage.

### Agent-facing high-fidelity lane

An AI model does not have intrinsic access to Confluence. It needs an
authenticated API tool with the relevant `READ` and, for an approved update,
`UPDATE` permission. When that tool is available, direct Storage editing is
the more reliable agent path for constructs whose fidelity matters: macros,
task lists, complex tables, resource identifiers, and presentation attributes.

Do not make the model's remembered XML or macro syntax the source of truth.
Start from the latest `body.storage.xml` retrieved from the target Cloud site,
change only the reviewed scope, and let the Cloud read-back establish the
accepted normalization. In particular, do not invent a third-party macro or
overwrite a server-managed identifier merely because a similar fragment is
known from another page.

The resulting operating model is **Markdown-first, Storage-authoritative for
fidelity**:

- people write and review ordinary content in Markdown;
- agents use the matching Storage snapshot and sidecars to preserve opaque
  constructs;
- agents enter the direct Storage lane only for an explicitly scoped,
  high-fidelity change, then retain submitted and normalized bodies as a
  fixture pair.

This is not a claim that every Storage construct is safe to synthesize. It is
a disciplined way to make a known, observed construct reproducible while
keeping normal authoring readable.

For a direct Storage update:

1. capture the current page and version in an immutable snapshot
2. create a separate candidate Storage fragment; never edit the snapshot
3. validate the fragment as XML with `ac` and `ri` namespace bindings
4. calculate and retain a SHA-256 digest for the reviewed candidate
5. set the requested version to the current version plus one
6. run `api.v2.updatePage` with `--dry-run`
7. present the exact target, title, version, scope, exclusions, diagnostics,
   and candidate digest
8. stop until the user explicitly approves that reviewed candidate
9. revalidate the candidate digest and live page version immediately before
   applying
10. apply once with `--allow UPDATE` and `--confirm-destructive`
11. read the page back and record postcondition evidence

Dry-run validates the operation and request contract locally. It does not
prove that Confluence Cloud will accept every Storage construct, so the live
apply and postcondition remain distinct steps.

## Permission gates

There are two independent local permission gates.

- The call must include `--allow UPDATE`.
- `MIKU_CONFLUENCE_ALLOWED_PERMISSIONS` must also contain `UPDATE`.

When `MIKU_CONFLUENCE_ALLOWED_PERMISSIONS` is absent, the runtime defaults to
`READ`. Passing only `--allow UPDATE` therefore produces
`PERMISSION_REQUIRED` before a remote request is sent.

Treat that result as `not-applied`, preserve it as attempt evidence, and do not
retry automatically. A retry requires a new explicit user instruction. For an
exact reviewed update, a process-scoped `READ,UPDATE` setting avoids silently
persisting broader permissions in `.env`; it must not become a general default.

Always inspect the JSON result envelope's `success` value. A shell pipeline
that ends in a formatter such as `jq` can otherwise hide the runtime command's
non-zero exit status.

## Postcondition and server normalization

Confluence may normalize accepted Storage by removing insignificant
whitespace, normalizing namespace declarations, adding identifiers, or
rewriting equivalent markup. The returned Storage therefore does not need to
be byte-for-byte identical to the submitted candidate.

One Cloud read-back observation was that `data-font-size="small"` remained,
while `data-font-size="large"` was removed and its paragraph became the normal
size. Do not infer accepted font-size variants from XML validity or dry-run
alone. Use a controlled candidate containing labeled variants, then compare
the normalized live Storage after applying it.

A controlled presentation-variant update applied on 2026-08-05 also showed
that Cloud rewrites pixel values such as `font-size: 10px` to
`font-size: 10.0px`, and compacts whitespace between CSS declarations. It
preserved the tested foreground colors, background colors, text alignment, and
indentation values. The Markdown export from the normalized page recorded 49
preserved attributes, including 36 presentation-attribute warnings and no
conversion errors.

The durable, sanitized fixture belongs in the upstream implementation
repository at
`test/fixtures/contracts/presentation-variants-cloud-normalization/`. It keeps
the submitted fragment and the Cloud-normalized fragment as a pair. Tests use
the normalized fragment as the conversion input; the submitted fragment exists
to make the server-normalization contract explicit.

Postcondition checks should confirm:

- page ID, status, title, and expected new version
- body representation is `storage`
- representative structural markers from the reviewed scope remain present
- required macros, task lists, tables, links, and final sections exist
- diagnostics contain no unresolved error

After a successful update, retain the previous run as the immutable pre-update
baseline. Start a new read-only run when continued editing needs the normalized
server state as its base.

## Workplace evidence

Keep the reviewed candidate and every attempt under the same edit run.

```text
workplace/miku-confluence/pages/page-<page-id>/runs/<run-id>/
├─ markdown/
└─ artifacts/
   ├─ snapshot/
   ├─ plans/
   │  └─ storage-coverage-update-001/
   │     ├─ candidate.storage.xml
   │     └─ review.md
   └─ attempts/
      └─ storage-coverage-update-001/
         ├─ attempt-001.json
         └─ attempt-002.json
```

Record a locally blocked attempt separately from a successful remote attempt.
Do not overwrite either result, even when the first attempt sent no request.

## Implications for tests

Future coverage tests should use explicit fixture groups rather than one
ever-growing page.

- Markdown-native fixture
- presentation-attribute fixture
- opaque core Storage fixture
- macro fixture
- table and layout fixture
- attachment and resource-identifier fixture

For every fixture, report recognition, projection, preservation, and editable
round-trip coverage separately. This makes unsupported editing visible without
misclassifying exact opaque preservation as data loss.
